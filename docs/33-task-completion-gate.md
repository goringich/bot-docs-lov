# Task completion gate

> [!important] Definition of done
> Работа считается завершённой не после изменения файла и не после локального
> теста, а после получения прямого доказательства каждого слоя, который
> относится к запросу пользователя.

## 1. Единственные terminal states

| State | Когда разрешён | Что писать пользователю |
|---|---|---|
| `COMPLETE` | Есть подтверждение всех применимых строк из таблицы ниже. | Кратко: результат, команды/наблюдения и доказанный business outcome. |
| `BLOCKED` | Нужный слой невозможно выполнить после безопасных in-scope попыток. | Точный недостающий доступ или факт, уже сделанные проверки и один узкий запрос, который разблокирует продолжение. |

Нет третьего «почти готово». Слова «готово после рестарта», «можно задеплоить»
и список неисполненных команд означают `BLOCKED`, а не `COMPLETE`.

## 2. Матрица доказательств

| Слой | Когда применим | Минимальное доказательство |
|---|---|---|
| Scope и изменение | Всегда, если менялся код/конфигурация/документ | Проверен конкретный путь и diff решает исходную причину, а не симптом. |
| Автотесты | Любое изменение поведения или кода | Узкие regression tests с реальной формой входа; для risky areas — обязательный preflight из [[09-testing-strategy]]. |
| Build / syntax | Изменён исполняемый subsystem | Соответствующий typecheck, lint, compile или build завершился успешно. |
| Deploy / migration / restart | Изменение должно работать в запущенном runtime | Фактически выполненный deploy/restart/migration на нужном окружении, без незафиксированной ошибки. |
| Live technical health | Есть runtime/API/UI/worker | Актуальный health/readiness/log/response после deploy, а не старый снимок. |
| Live business outcome | Пользователь просил изменить данные или поведение | Проверен именно эффект: например, catalog закрыт в реальной БД/API, сообщение обработано, экспорт создан или UI показывает новое состояние. |

Не подменяй строку таблицы другой: unit test не заменяет deploy; `200 /health`
не доказывает закрытие каталога; успешный restart не доказывает, что нужная
запись исправилась.

## 3. Последовательность работы

1. Сначала назвать применимые строки матрицы. Для чисто документационной задачи
   не нужны Docker/API checks; для parser/catalog/order/data-задачи обычно
   нужны все строки до live business outcome.
2. Выполнить изменение и самый узкий regression test. Исправить новую ошибку,
   а не обходить её `skip`, ослаблением expectation или чужим workaround.
3. Выполнить обязательные build/preflight checks и проверить startup, volume,
   env/subprocess paths, если они участвуют в runtime.
4. Если задача требует живого результата — применить изменение в нужном
   окружении, затем проверить health и точный business effect.
5. Если шаг заблокирован, сначала проверить безопасные доступные способы
   продолжить. Если их нет, завершить только состоянием `BLOCKED` с
   воспроизводимым доказательством блокера и минимальным запросом доступа.

## 4. Особое правило для parser / catalog / orders

Для изменения парсера или lifecycle каталога локальная suite подтверждает
только код. `COMPLETE` требует также:

- запущенный worker/admin API с новым образом;
- подтверждение, что применена нужная migration (если есть);
- проверку через фактический DB/API state именно затронутого catalog/order;
- проверку, что intake/worker сделал нужное действие, а не только вернул
  здоровый HTTP endpoint.

Пример: «закрыть каталог, который должен был закрыться 13-го» завершён только
после того, как выбранный catalog имеет закрытый intake (`closed_at`/status) в
живом источнике и новые заказы не принимаются. Новый тест и код без доступа к
этому состоянию — `BLOCKED`.

Для компактного доказательства после read-only DB/API query можно использовать
`backend/scripts/verify_catalog_lifecycle.py`. Скрипт принимает только
`catalog_id`, `status` и опциональный `closed_at`, не читает config/DB и не заменяет сам
live query. Отсутствующий `closed_at` даёт явный failed proof, а некорректная
дата отклоняется с понятной ошибкой — ни один из этих случаев не может быть
засчитан как закрытие.

## 5. Формат финального сообщения

```text
Completion state: COMPLETE | BLOCKED

Verified:
- <evidence tied to an applicable layer>

Remaining / blocker:
- <nothing, or exact missing capability and next action>
```

Не объявляй весь проект «проверенным», если проверялась только изменённая
подсистема. «Все проверки» означает все проверки, применимые к исходному
запросу, а не бесконечный запуск несвязанных suites.

## 6. Защита контракта

Запусти `make check-agent-contract` после изменения этого runbook, `AGENTS.md`,
`CLAUDE.md`, Copilot instructions или runner-а проверок. Скрипт проверяет, что
все agent entry points по-прежнему ссылаются на этот gate; он не заменяет
фактические тесты, deploy или live verification.
