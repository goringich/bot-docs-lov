# Excel export (актуально на 2026-04-06)

Экспорт в Excel строится на основе данных в БД и предназначен для работы админов (закупка/сборка/раздача).

## Реализации

### 1. Бот-экспорт (backend)
- `backend/app/excel_export.py`
- Тесты: `backend/tests/test_excel_export.py` (20 тестов)
- Команды: `/export_items`, `/export_pickup`, `/export_xlsx`

### 2. Операционный экспорт (admin_service, legacy)
- `Orders → 📥 Экспорт заказов` — `GET /orders/export` (4 листа)
- `Orders → 📜 Экспорт истории` — `GET /orders/export-history` (3 листа: история заказов, строки, аудит)
- `Orders → 📄 Экспорт по шаблону` — `GET /orders/export-template` (по `samples/excel/template.xlsx`)

### 3. Комплексный экспорт-конструктор (admin_service, новый)
- Страница **«📥 Экспорт данных»** в навигации (доступна owner + regional_admin)
- `GET /exports/presets` — возвращает каталог доступных листов и готовые шаблоны
- `POST /exports/build` — собирает multi-sheet XLSX из выбранных типов листов

#### Фильтры (per-sheet и глобальные)

Каждый лист поддерживает:
- `catalog_id` — фильтр по каталогу
- `chat_id` — фильтр по чату
- `pickup_place` — фильтр по точке выдачи
- `date_from`, `date_to` — диапазон дат (YYYY-MM-DD)
- `limit` — максимум строк

На фронтенде: глобальные фильтры (каталог, чат, даты) + per-sheet фильтры через кнопку ⚙️.
- точка выдачи (`pickup_place`)
- статус заказа (`status`)
- диапазон дат (`date_from`, `date_to`)
- текстовый поиск (`search`: имя, телефон, точка, текст сообщения)

## Режимы экспорта

Функция экспорта поддерживает `mode`:

- `full` — полный файл с детальными строками и сводками
- `assembly` — файл для сборки: фокус на позициях и агрегировании
- `pickup` — файл для выдачи: фокус на разрезе по точкам
- `template` — **экспорт по шаблону** (`GET /orders/export-template`): загружает `samples/excel/template.xlsx` как базу, заполняет данными заказов. Позволяет использовать кастомное оформление.

### Export by Template

Endpoint: `GET /orders/export-template`

- Берёт `samples/excel/template.xlsx` как базовый файл (шапка, стили, логотип)
- Заполняет данные заказов начиная с первой пустой строки
- Колонки: ID, Имя, Телефон, Точка выдачи, Статус, Дата, Позиции
- Принимает те же фильтры что и основной экспорт

### Strict / distribution template export

Endpoints:

- `GET /orders/export-template-strict`
- `GET /orders/export-template-distribution`

#### Жёсткий формат шаблона (контракт)

Шаблон экспорта **строгий** и закреплён:

| Колонка | Заголовок | Источник |
|---------|-----------|----------|
| 1 | **Имя** (клиент) | `orders.customer_name` |
| 2 | **Телефон** | `orders.phone_last4` (последние 4 цифры) |
| 3 | **Точка выдачи** | `orders.pickup_place` |
| 4 | **Текст заказа** | `orders.raw_text` (исходное сообщение клиента) |
| 5… | Товарные колонки | **Заголовки строго из каталога** (`catalog_items.title`) |

Правила колонок:

- Первые **4 служебные колонки фиксированы** и не зависят от шаблона: имя, телефон, точка выдачи, исходный текст заказа.
- В 4-ю колонку всегда пишется `orders.raw_text`; fallback из собранных строк заказа / `order_no` используется только если raw-текста нет.
- Все товарные колонки начиная с 5-й — это позиции **только из каталога** (`catalog_items`), отсортированные по `position_order`. Никакие позиции, отсутствующие в каталоге, не появляются как новые колонки.
- Заголовки этих колонок берутся **строго** из `catalog_items.title` и не редактируются в шаблоне на лету.
- Связка строки заказа с колонкой делается только через `catalog_item_id` / SKU; fuzzy-match идёт по алиасам каталога.
- Если строка заказа не нашла каталожного соответствия, она остаётся в колонке `Текст заказа` и **не создаёт новую колонку справа** (для `template-distribution` это жёсткое правило).

#### Привязка экспорта к датам каталога

- При выборе `catalog_id` дата работы каталога (`catalogs.opened_at` … `catalogs.closed_at`) становится источником истины: в выгрузку попадают только заказы, чьи `source_message_ts` / `created_at` попадают в это окно.
- Пользовательские `date_from`/`date_to` опциональны и **сужают** окно каталога; они не могут расширить его.
- Если `date_from`/`date_to` не заданы — окно каталога применяется как есть.
- Без выбранного каталога фильтрация идёт строго по пользовательскому диапазону (как раньше).
- Поля `date_from`, `date_to`, `pickup_place` помечены в UI как **необязательные** и могут быть скрыты целиком (см. Sysadmin → «Экспорт» → `export_filter_show_date_range`, `export_filter_show_pickup`).

#### Прочие инварианты strict/distribution

- используют **первый лист живого Excel-шаблона** как основную таблицу 1:1;
- перед сохранением workbook принудительно схлопывается до **одного рабочего листа**: лишние листы из исходного шаблона не попадают в итоговый export;
- сохраняют первые 4 служебные колонки как `Клиент / Телефон / Точка / Состав заказа`, но в 4-ю колонку пишут **исходное сообщение клиента (`orders.raw_text`)`**; если raw-текст отсутствует, только тогда используется fallback из собранных строк заказа / `order_no`;
- заполняют товарные количества по заголовкам из шаблона и fuzzy-match по сокращениям/алиасам;
- если строка заказа связана с `catalog_item` / SKU, источником истины для количества и единицы считается сам каталог (`catalog_items.title + unit_hint + pack_hint`), а не текст сообщения пользователя и не числовые куски в заголовке вроде `125ГР` или `1200 Г`;
- в таком каталого-ориентированном режиме количество перед записью всегда приводится к **единице каталога**, даже если внешний template header использует другую нотацию; header влияет только на поиск колонки, но не на семантику количества;
- если безопасного преобразования к единице каталога нет, значение не должно silently притворяться другой единицей;
- для дискретных единиц (`шт/уп/банка`) export не должен silently превращать количество в граммы или дробные псевдо-упаковки; несовместимые значения остаются в `Состав заказа` и не должны искажать числовую товарную колонку;
- если строка не связана с каталогом вообще, допускается только сырой числовой fallback без перепридумывания единиц по header text;
- для `export-template-strict`: если позиция из заказа **не нашла колонку в шаблоне**, справа добавляется overflow-колонка с названием позиции;
- для `export-template-distribution`: экспорт остаётся **строго каталого-ориентированным**; не-каталожные / несматченные строки не должны создавать новые overflow-колонки справа и не должны расширять шаблон вне каталожной сетки;
- для режимов 1:1 товарные колонки после четвёртой автоматически ужимаются до компактной ширины, достаточной для 3–4-значных значений;
- финальная выдача очищает inherited template noise: цветные заливки, conditional formatting/table tails и пустой хвост за рабочей областью (`AL...`, пустые `AM...`) удаляются до сохранения файла.

## Инварианты источника истины

- Источник истины для товарного naming/order/export — **текст каталога, который оператор вставил и из которого был создан каталог**.
- Каталог под уже существующие заказы **не переписывается** ради матчинга/экспорта.
- После создания каталога вручную допускается расширять только `aliases`, если нужен дополнительный распознаваемый вариант названия.
- Текстовые фрагменты веса/фасовки внутри названия (`125ГР`, `0.5`, `1кг`) — это часть имени позиции, а не отдельная команда export-слою переписать structured quantity в граммы.
- Excel-шаблон влияет только на внешний вид и сетку колонок; бизнес-единицы и порядок позиций диктуются каталогом/БД.

### Export History (audit)

Новый endpoint: `GET /orders/export-history`

Содержимое:
- `orders_history` — полная история заказов (включая `raw_text`, `error_text`, timestamps)
- `lines_history` — полная история строк заказа (включая line status/errors)
- `audit_summary` — свод по статусам заказов и строк

Использование: сверка, расследование инцидентов, сравнение с “ручной конечной таблицей”.

### Query filters для admin export API

Оба admin endpoint-а поддерживают одинаковые query-параметры:

- `GET /orders/export`
- `GET /orders/export-history`

Важно: эти маршруты являются **статическими** и не должны пересекаться с `GET /orders/{order_id}`. Если после деплоя/обновления API экспорт продолжает отдавать `422` с попыткой распарсить `export` как `order_id`, значит запущен старый экземпляр `admin_service` и его нужно перезапустить.

Поддерживаемые параметры:
- `catalog_id`
- `chat_id`
- `pickup_place`
- `status`
- `date_from=YYYY-MM-DD`
- `date_to=YYYY-MM-DD`
- `search`

`date_to` включителен на уровне дня: для даты `2026-03-09` backend выгружает всё до конца этого дня.

## Содержимое листов

Набор листов зависит от режима, структура:

### Лист «Заказы» (режимы: full, pickup)
| Колонка | Описание |
|---------|----------|
| ID | Номер заказа |
| Имя | Имя покупателя |
| Телефон | Телефон |
| Точка выдачи | Pickup place |
| Статус | Emoji-статус (✅ Подтверждён, ⏳ Ожидает, ❌ Отклонён и т.д.) |
| Дата | Форматирована dd.MM.yyyy HH:mm |
| Позиции | Список товаров через запятую |

### Лист «Позиции» (режимы: full, assembly)
| Колонка | Описание |
|---------|----------|
| Заказ # | ID заказа |
| Покупатель | Имя |
| Артикул | SKU |
| Товар | Название |
| Кол-во | Числовое |
| Ед. | Единица измерения |
| Цена | Текст из снапшота |
| Статус строки | Emoji-статус |

### Лист «Сводка товаров» (режимы: full, assembly)
Агрегация по товарам: Артикул, Товар, Общее кол-во, Единица, Кол-во заказов.
Строки с qty > sanity-порогов (`_MAX_SANE_QTY`) исключаются из агрегации.

### Лист «По точкам» (режимы: full, pickup)
Агрегация по точкам выдачи: Точка выдачи, Кол-во заказов, Покупатели (перечень имён).

## Оформление

- **Title row**: объединённая ячейка с названием каталога + датой генерации, синий фон
- **Header row**: синий фон (#4472C4), белый жирный шрифт, center alignment
- **Data rows**: zebra-striping (чередующиеся белый/светло-голубой #F2F7FB)
- **Auto-width**: колонки автоматически подстраиваются под контент (min 10, max 50)
- **Freeze panes**: заморозка строк заголовка для прокрутки
- **Auto-filter**: фильтрация по всем колонкам

## Примечания

- Для воспроизводимости экспорт использует снапшоты в `order_lines` (`item_sku`, `item_title`, `price_text_snapshot`).
- Проблемные строки (`bad_qty/unknown_item/stopped`) как правило не должны попадать в “закупку”, но полезны для аудита.
