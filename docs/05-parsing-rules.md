# Parsing rules (актуально на 2026-07-15)

Эта страница описывает пользовательский формат заказа и как бот интерпретирует текст.

Смотри реализацию:
- парсер: `backend/app/parser/text_parser.py`
- доменная логика/эвристики: `backend/app/domain/order_domain.py`
- матчинг каталога (+ typo-коррекция): `backend/app/repo/catalog_repo.py`
- тестовые примеры реальных заказов: `backend/tests/test_samples.py`
- **комплексные тесты на реальных данных**: `backend/tests/test_real_messages.py` (63 теста из реальных Telegram-сообщений)
- **тесты новых фич парсера**: `backend/tests/test_parser_upgrade.py` (58 тестов — слитный ввод, emoji, отмены, опечатки, edge cases)

## 1) Общая идея

Пользователь пишет текстом несколько строк. Бот пытается выделить:
- позиции (товар + количество)
- точку выдачи
- последние 4 цифры телефона
- имя клиента

Если не хватает обязательных данных или есть ошибки в строках — бот отвечает подсказкой.

## 2) Поддерживаемые форматы заказов

Бот распознаёт различные форматы записи заказа (все обучены на реальных данных из `samples/telegram/`):

### Стандартный многострочный формат
```
Имя XXXX
Точка
Товар1 Xкг
Товар2 Xшт
```

### Формат с точками (all-in-one line)
```
Имя XXXX.Точка.Товар1 Xкг.Товар2 Xшт.
```

### Формат header + items (через запятую)
```
Имя XXXX Точка
Товар1 - Xкг, Товар2 - Xшт
```

### Обратный порядок (точка сначала)
```
Точка, XXXX, Имя, товар1 Xкг, товар2 Xшт
```

### Телефон в начале
```
XXXX Имя Точка
Товар Xкг
```

### Телефон в конце сообщения
```
Товар1 Xкг
Товар2 Xшт
Имя XXXX Точка
```
Бот обнаруживает телефон в любой строке и переставляет метаданные наверх при препроцессинге.

### Нумерованные списки
```
Имя XXXX Точка
1) Товар1 - X кг
2) Товар2 - X шт
```
Также: `1.Товар`, `1-Товар`, `1 Товар` с нумерацией на той же строке.

### Нумерованный список в одну строку
```
Имя XXXX. Точка. 1) Товар1 X кг. 2)Товар2 X шт
```
Препроцессор разбивает нумерованные элементы по отдельным строкам.

### Без точки выдачи (Arzamas-формат)
```
Имя XXXX
Товар1 Xкг
Товар2 Xшт
```

### Дозаказ
```
Дозаказ
Имя XXXX
Товар Xкг
```
Или `До заказ`, `дозаказ` — метка удаляется при парсинге.

### С ценами (цены отбрасываются)
```
Горбуша 2кг 950р
Минтай 3кг 485руб
Креветки 1уп 370р/кг
```
Парсер автоматически удаляет цены (`950р`, `485руб`, `370р/кг`, `по 450`, `950 за кг`).

Если это **служебный пост / прайс-лист без клиентских метаданных**, сообщение с одними ценами (`Икра трески 150 руб`) заказом не считается.

Если же это **короткий клиентский заказ** с именем, 4 цифрами телефона и точкой выдачи, то для штучных/баночных/упаковочных позиций бот может принять строки вида `Икра трески 150 руб` как заказ по умолчанию на `1` единицу. Хвосты вроде `Спасибо🙏` при этом игнорируются.

Дополнительно бот теперь понимает краткую форму без числа для упаковочных позиций, если количество явно подразумевается: `карт.фри -упак.`, `икра трески - банка`, `пельмени - пачка` → это трактуется как `1` единица соответствующего типа.

## 3) Позиции (товар + количество)

Типовой формат:

- `Минтай 2 кг`
- `Креветки 1 уп`
- `Форель 3 шт`
- `Скумбрия х/к 2 шт` (с модификатором х/к = холодного копчения)
- `Горбуша св.мороженая 1 кг` (с модификатором)

Разделители допускаются разные: пробелы, тире, двоеточие. Главное — чтобы можно было выделить *название* и *количество*.

### Что считается количеством

Поддерживается “человеческий” ввод:
- `0.5 кг`, `0,5 кг`
- `0,5-1 шт` — сохраняется как диапазон количества/размера без загрязнения `title_raw`
- `полкило`, `пол кило` → `0.5 кг`
- `полтора`, `полторы` → `1.5`
- `пара`, `две`, `два`, `один/одна` → `2/2/1`
- словесные числа: `три`…`десять` → `3`…`10`
- формат `1кг200г` → интерпретируется как вес (пример: `1.2 кг` в нормализованном виде)
- **формат фасовок**: `2×250г`, `2x250г`, `3*500г` → вычисляется итог (`500 г`, `1.5 кг`); при ≥1000г автоматическая конвертация г→кг

Нормализованное текстовое представление количества кладётся в `OrderLine.qty_value_text`.

### Единицы измерения

Бот использует единицы (внутренний enum):
- `kg` (кг)
- `g` (гр)
- `pcs` (шт) — также: `тушка`/`тушки`, `рыбка`/`рыбки`, `штука`/`штук` → нормализуется в `шт`
- `pack` (уп) — также: `пачка`/`пачки`, `коробка`/`коробок` → нормализуется в `уп`
- `can` (б/банка) — также: `баночка`/`баночек`
- дополнительно: `палка`, `стакан`, `ведро`, `пластина`, `кусок`, `л`, `мл` — всего ~60 нормализаций

Также поддерживаются разговорные сокращения вроде `1бан`, `2бан.` → нормализуются в `банка`.

Если единица не распознана или значение некорректно — строка получает статус `bad_qty`.

### Sanity-пороги количества (добавлено 2026-07-15)

Чтобы предотвратить парсинг телефонных номеров и других длинных чисел как количества, в `parse_qty()` встроены пороги `_MAX_SANE_QTY`:

| Единица | Максимум |
|---------|----------|
| кг | 100 |
| г | 50 000 |
| шт | 200 |
| уп | 100 |
| банка | 100 |
| л | 50 |
| мл | 50 000 |
| (без единицы) | 500 |

Если распознанное значение превышает порог → функция возвращает `(None, None, None)`, и строка получает статус `bad_qty`. Это защищает от случаев вроде «Елена 4424 Иваново 2» → qty 4424000.

Дополнительно: `_IMPLICIT_SINGLE_UNIT_RE` (неявное `1 шт/уп/банка`) теперь срабатывает **только** когда в фрагменте нет числа, чтобы «3 банки» не превращались в «1 банка».

### Предобработка текста (Smart Preprocessing)

Перед основным парсингом сообщение проходит через `_smart_preprocess_text()`:

1. **Emoji bullets** — удаление emoji-маркеров в начале строк (🐟, 🦐, 🔥, ✅ и т.д.)
2. **Слитный ввод** — разделение:
   - `Ольга8493` → `Ольга 8493` (имя+телефон)
   - `8086Ванеева` → `8086 Ванеева` (телефон+место)
   - `НатальяЩербинки` → `Наталья Щербинки` (имя+место, через known_places)
3. **Inline header перед товаром** — если сообщение приходит как `Имя Точка Товар qty`, заголовок отделяется от товарной части по первому product keyword.
   - особенно важно для alias-ов точек с цифрами: `Наталья Иваново 2. Горбуша свежемороженая-1шт` больше не превращается в ложное количество `2` у первой строки
   - если телефона нет, имя всё равно может быть извлечено из такого inline-header при наличии распознанной точки выдачи
3. **Символ `=` как разделитель** — `Форель=2кг` → `Форель 2кг`
4. **Скобочные комментарии** — `Форель (если свежая) 2кг` → `Форель 2кг`

### Коррекция опечаток в каталоге

`catalog_repo.py` содержит карту частых опечаток (`_TYPO_MAP`):
- `комбала` → `камбала`
- `троска` → `треска`
- `менитай` / `минитай` → `минтай`
- `игра` → `икра`
- `лосось` / `лойоны` → корректные формы

Коррекция применяется **перед** fuzzy matching (Levenshtein distance), что повышает точность.

### Сопоставление товара

Товар сопоставляется с `CatalogItem` текущего каталога по:
- точному SKU (когда пользователь пишет SKU), или
- названию/алиасам.

Если товар не найден — строка получает статус `unknown_item`.

## 3) Стоп-лист

Если товар остановлен (`CatalogItem.is_active=0`):
- строка получает статус `stopped`.

Если задан временный стоп `stop_until` и он уже истёк — строка может быть принята (статус `ok`).

Важно: авто-снятие стопа как изменение записи товара — отдельная задача (пока это только поведение при обработке).

## 4) Эвристика “похоже на заказ”

Чтобы не мешать обычным разговорам в чате, бот сначала пытается понять, что сообщение похоже на заказ.
Если нет — игнорирует.

Реализация: `looks_like_order` в `backend/app/domain/order_domain.py`.

### Scoring-based подход (v2, 2026-06)

Вместо жёстких правил используется система баллов:

### Положительные сигналы

| **Сигнал**                                                    | **Баллы** |
| ------------------------------------------------------------- | --------- |
| Ключевые слова товаров _(рыба, морепродукты, мёд - ~80 слов)_ | +3        |
| Телефон _(4+ цифр подряд)_                                    | +2        |
| Точка выдачи _(известное место)_                              | +2        |
| Строки с количеством _(≥2 строк)_                             | +2…+3     |
| Имя клиента _(из списка известных имён)_                      | +1        |
| Ключевое слово **«дозаказ»**                                  | +3        |

Дополнительный guard: если в сообщении **нет товарного ключевого слова** и одновременно нет клиентской идентификации (имя/телефон/точка), то одиночная строка с весом сама по себе заказом не считается. Это отсеивает отзывы вида `Рыбина на 3.850 кг. с бонусом`, которые раньше могли пройти как заказ только из-за qty-паттерна.

**Порог**: score ≥ 3 → считается заказом.

### Фильтрация не-заказов

Следующие сообщения автоматически отклоняются (`_NON_ORDER_PATTERNS`):
- Приветствия: `здравствуйте`, `добрый день`, `привет`
- Вопросы: `есть ли`, `когда будет`, `можно ли`, `подскажите`, `сколько стоит`
- Жалобы: `не то привезли`, `качество`, `возврат`
- Рецепты/посты: длинные сообщения (>10-15 строк), URL, emoji-heavy
- Стоп-анонсы / служебные посты: `внимание`, `заказы на данные позиции больше не принимаем`, многократный `стоп` с warning emoji
- Прайс-листы без qty: несколько строк формата `товар + цена`, но без клиентских метаданных
- **Отмены и изменения заказов** (`_CANCEL_PATTERNS`): `отказ`, `отменить`, `убрать`, `замена`, `вместо`, `не смогу забрать` — 7 паттернов. Такие сообщения требуют ручной обработки администратором.

### Длинные сообщения

`_looks_like_recipe_or_post()` отсеивает рецепты, админские объявления и длинные посты:
- Сообщения с ❗️❗️❗️ или фразами типа «в свободной продаже» — admin posts
- stop/announcement posts с `не принимаем` и повторяющимся `стоп` — тоже не проходят как заказы
- >15 строк с товарными словами или >10 без → скорее всего не заказ
- Короткие сообщения с товаром + количеством всегда пропускаются

Дополнительно `+` внутри размерного маркера (например `Креветки 250+ 1уп`) больше не считается разделителем между товарами.

## 5) Результат парсинга

Для каждой строки `OrderLine.status`:
- `ok` — принята
- `stopped` — товар в стоп-листе
- `unknown_item` — не нашли товар в каталоге
- `bad_qty` — не распознали количество/единицу

Для заказа `Order.status`:
- `active` — принят целиком или частично (есть `ok` позиции)
- `needs_admin` — нужно вмешательство (не хватает данных, есть проблемы)
- `canceled` — отменён

## 6) Профиль пользователя

Если пользователь ранее сохранял профиль (`/set_pickup`, `/set_phone`) — бот может автоматически
подставить недостающие поля (точка выдачи/телефон/имя). Это снижает число `needs_admin`.
