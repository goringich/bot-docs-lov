# Admin panel (web) — overview

Дата: 2026-06-18

Цель: выделить управление доступами и данными из Telegram‑чата в веб‑интерфейс.

### Персональный внешний вид

- Тема, режим `light/dark` и стиль интерфейса теперь сохраняются отдельно для каждого пользователя.
- Настройка внешнего вида доступна из пользовательского меню и не требует owner-доступа к системным настройкам.
- Это важно для общих компьютеров и сменной работы: один сотрудник больше не меняет оформление сразу «для всех» в этом браузере.

### Ограничения owner-only разделов

- Экспорт XLSX и системные security/owner-настройки остаются owner-only на backend.
- UI теперь не показывает региональным администраторам owner-only экспорт, даже если роль когда-то была ошибочно добавлена в visibility-настройки: это убирает лишние `403` и `429` в рабочем интерфейсе.
- Роут `/export` дополнительно зафиксирован как owner-only на уровне клиентского роутинга: прямой переход по URL для non-owner теперь возвращает в доступный рабочий раздел вместо экрана с backend-ошибкой.

### API и эндпоинты: теперь это документация, а не экран в продукте

- Каталог endpoint-ов вынесен из интерфейса `admin-web` в developer-docs.
- Основной документ: [[17-admin-service-endpoints-manual]].
- Расширенный reference с контекстом и RBAC-деталями: [[14-api-reference]].
- Source of truth для route-ов и request fields по-прежнему лежит в `admin-web/src/api/apiCatalog.ts`.

## Компоненты

- `admin_service` (FastAPI) — RBAC, JWT, API для админ‑панели.
- `admin-web` (React + Vite + MUI) — интерфейс.

## Назначение админки

Админка рассматривается не как витрина поверх бота, а как основное рабочее место операционной команды. Через неё должны выполняться повседневные сценарии сопровождения заказов, управления каталогами, выдачи, настроек доступа и контроля безопасности.

Ключевые требования к админке:

1. Быстрый доступ к операционному состоянию.
Пользователь должен быстро понимать, что происходит в системе: где новые заказы, где проблемные строки, где зависла выдача, где требуется вмешательство администратора.

2. Разделение интерфейса по реальной ответственности ролей.
Owner управляет системой, доступами и рисками. Manager работает с заказами и исключениями. Pickup admin работает в сценарии выдачи. Regional admin координирует локальную операционку без доступа к owner-only функциям.

3. Перенос чувствительных действий из Telegram в web-контур.
Экспорты, аналитика, управление ролями, системные настройки и аудит должны выполняться только в административном интерфейсе, где есть аутентификация, подтверждение критичных действий и журналирование.

4. Ориентация на рабочие процессы, а не только на CRUD.
Интерфейс должен поддерживать реальные сценарии: открыть каталог, исправить заказ, перевести заказ в выдачу, разобрать проблемную строку, проверить кто и что менял, ограничить доступ или подтвердить чувствительную операцию.

В проектных терминах админка должна рассматриваться как backoffice-система, а не как набор экранов для редактирования таблиц.

## Роли и уровни доступа

- `owner` — полный доступ: управление ролями, каталогами, настройками, видимостью бота, аналитика.
- `regional_admin` — локальный супервайзер по городу/региону (операционка + помощь менеджерам/выдаче, в рамках назначенных чатов/городов).
- `manager` — работа с заказами и ошибочными строками (без системных настроек).
- `pickup_admin` — оператор выдачи (выдача и журнал, по закреплённым точкам).

## Основные функции

1) Login/Logout (JWT + one-time links из Telegram)
2) **Дашборд** — статистика заказов, топ-товаров, графики
3) **Заказы** — список, фильтры, детали, смена статуса, **📥 Excel экспорт** (XLSX с 4 листами + экспорт по шаблону), **✏️ полное редактирование заказа** (метаданные + построчное редактирование позиций: добавление, изменение, удаление строк)
4) **Каталоги** — CRUD каталогов и товаров, стоп-лист, aliases (с диалогами подтверждения удаления)
5) **Admin-Chat scoping** — назначение админов к чатам (owner-only)
6) **Аналитика** — recharts графики (AreaChart, PieChart, BarChart), breakdown по статусам, pickup-точкам, фильтрация по чатам. **Доступна только owner.**
7) **Пользователи** — CRUD админов, управление ролями, **регистрация** новых пользователей через пошаговую форму (с диалогами подтверждения удаления)
8) **Настройки** — bot_settings, pickup places, видимость бота в чатах, антиспам, **feature toggles** (owner-only). Организованы в 8 вкладок: Приложение, Бот, Точки, Интерфейс, Инструменты, Доступ, Система, **Журнал действий**.
9) **Excel Превью** — загрузка и предпросмотр уже готовых `.xlsx` файлов (owner-only)
10) **Debug** — тест парсера, статус системы
11) **Журнал действий** — просмотр audit log с фильтрацией по типу объекта и пагинацией (вкладка в Настройках)
12) **Выдача (DeliveryPage)** — рабочее место оператора выдачи с 4 вкладками:
    - **К выдаче** — очередь заказов с исходным текстом, составом, кнопками «Полностью / Частично / Передан»
    - **Журнал** — записи о выдачах с raw_text заказа, получателем, кем отмечено
    - **Отмеченные** — все обработанные заказы с исходным текстом, статусом выдачи
    - **Проблемы** — заказы с ошибками, проблемные позиции, исходный текст
    - Во всех вкладках — сворачиваемый `RawTextCell` для отображения исходного текста заказа

## Внутренняя архитектура админки

### Backend-часть

`admin_service` — отдельный сервис, а не набор вспомогательных endpoint-ов внутри бота. Он поднимается на `FastAPI`, работает со своей моделью доступа и использует общую БД как operational/read-write слой.

Что важно внутри:

- аутентификация вынесена в `auth`-роутер;
- роли и пользователи живут отдельно;
- заказы, каталоги, настройки, выдача, экспорт и аналитика разнесены по отдельным роутерам;
- в сервисе есть собственные middleware для rate limiting, security headers и audit logging;
- чувствительные действия подтверждаются отдельно, а не только через базовый JWT.

### Frontend-часть

`admin-web` — отдельное SPA на `React + TypeScript`.

По факту фронт состоит из трёх слоёв:

- `src/api/client.ts` — typed API client, токены, Excel fallback-логика, обработка ошибок;
- `src/App.tsx` + `src/components/MainLayout.tsx` — shell приложения, RBAC-навигация, session guard, theme/style state;
- `src/pages/*` и `src/components/*` — прикладные рабочие экраны: заказы, каталоги, пользователи, настройки, выдача, экспорт, debug.

Такое разделение даёт понятные границы: API-клиент отдельно, shell приложения отдельно, прикладные страницы отдельно.

## Реализованный функциональный контур

По текущему коду админка уже покрывает основной операционный контур проекта, а не является прототипом под будущее развитие.

### Разделы и модули

- `OrdersPage` — список заказов, фильтры, просмотр деталей, редактирование заказа и строк, удаление, экспорт;
- `DeliveryPage` — очередь выдачи, частичная выдача, передача другому лицу, журнал выдачи, проблемные заказы;
- `CatalogsPage` — каталоги, товары, стопы, алиасы, CRUD по составу каталога;
- `UsersPage` и `RegisterPage` — пользователи, роли, регистрация, управление доступом;
- `SettingsPage` — настройки бота, точки выдачи, feature toggles, секционная видимость, аудит, security dashboard;
- `AnalyticsPage` — owner-only аналитика по заказам;
- `ExportPage` и Excel preview/template flows — owner-only выгрузки;
- `DebugPage` — owner debug mode и служебные инструменты.

### API-модули `admin_service`

По роутерам сервис уже покрывает:

- `auth` — bootstrap, login, logout, one-time links, password confirmation;
- `users`, `roles` — управление пользователями и ролями;
- `orders` — список заказов, детали, patch/delete, работа со строками, экспорт;
- `deliveries` — выдача, журнал, ошибки, назначения операторов точкам;
- `catalogs` — каталоги, товары, stop/unstop, clone;
- `settings`, `admin_settings` — bot settings и служебные настройки;
- `analytics` — owner-only статистика;
- `templates`, `exports` — шаблоны и экспортные сценарии;
- `spam` — антиспам-контур;
- `integrations` — M2M и служебные интеграционные точки.

## Целевая модель работы

Для каждого типа пользователя в системе должен существовать собственный короткий рабочий контур, а не общий перегруженный интерфейс.

Для `owner`:

- контроль доступа;
- контроль настроек;
- контроль экспортов;
- контроль аудита и security-событий;
- контроль того, что система в целом жива.

Для `manager`:

- только заказы;
- только проблемные строки;
- только нужные поля для ручной корректировки;
- без системного шума.

Для `pickup_admin`:

- один рабочий экран;
- крупные понятные действия;
- быстрый доступ к исходному тексту заказа;
- минимум лишних переходов;
- жёсткая привязка к своим точкам.

Для `regional_admin`:

- обзор локальной операционки;
- помощь менеджерам и выдаче;
- без доступа к owner-only функциям.

Смысл ролевой модели в админке состоит не в формальном скрытии пунктов меню, а в разделении ответственности и снижении операционного шума для каждой категории пользователей.

## Продуктовые принципы

- Админка должна быть главным местом работы с данными, а Telegram-бот — только каналом взаимодействия с пользователями и лёгкой операционкой.
- Любой чувствительный сценарий должен иметь audit trail.
- Любой экспорт должен быть осознанным действием, а не кнопкой без последствий.
- Любая роль должна видеть только свой рабочий контур.
- Любой экран выдачи должен быть быстрее, чем работа "по памяти" в чате и Excel.

### Глобальные UX-улучшения

- **ErrorBoundary** — глобальная обработка ошибок рендеринга React с дружелюбным fallback-UI
- **SnackbarProvider** — система тостов для обратной связи (успех/ошибка/предупреждение) вместо alert()
- **ConfirmDialog** — красивые MUI-диалоги подтверждения вместо native confirm() (используются в удалении каталогов, товаров, пользователей, назначений)
- **OrderEditDialog** — полноценный редактор заказа с отображением исходного текста, управлением метаданными, inline-редактированием строк, добавлением и удалением позиций

### Встроенные Excel-шаблоны

- В `admin-web` доступен локальный fallback-шаблон `template-3.xlsx`.
- Файл хранится в `admin-web/public/templates/template-3.xlsx` и используется как внутренняя резервная основа для экспорта.
- `template-3.xlsx` должен оставаться идентичным `samples/excel/template.xlsx`.
- Owner может заменить шаблон выгрузки, но UI не должен предлагать скачать его отдельно: пользовательская цель — скачать готовый Excel с заказами.
- При экспорте по шаблону образцовые строки из `template.xlsx` не должны попадать в результат: выгрузка очищает sample-body и заполняет лист новыми заказами, раскладывая позиции по товарным колонкам шаблона.
- Если `GET /orders/export-template` отвечает `404/500` или временно недоступен, `admin-web` автоматически собирает шаблонный экспорт на клиенте: берёт `template-3.xlsx`, догружает подходящие заказы/позиции через API и формирует итоговый `.xlsx` уже с данными заказов.

## Feature Toggles (owner-only)

Owner может управлять видимостью функций через Настройки → Управление функционалом:
- `feature_analytics_charts` — recharts графики в аналитике
- `feature_excel_preview` — Excel Превью страница
- `feature_raw_order_edit` — редактирование raw-данных заказов
- `feature_chat_grouping` — группировка/фильтрация по чатам
- `feature_registration` — регистрация новых пользователей

## Owner-only секции (UI)

Секции, доступные только owner, визуально отмечены:
- 👑 badge + жёлтый бордер слева в боковом меню
- Warning/owner-акценты на панелях настроек, доступных только владельцу

## Скрытый режим бота

Когда `bot_visible='hidden'` для чата:
- Бот обрабатывает заказы (парсинг, сохранение в БД)
- Бот **не** отправляет текстовые ответы и **не** ставит реакции пользователям
- Идеально для тестирования в реальных чатах без вмешательства
