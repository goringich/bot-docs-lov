# Admin flows (MVP)

## Goal
MVP: админы вручную заводят каталог (сбор) и позиции прайса в БД через команды в чате. Бот пока не отвечает в Telegram, но обрабатывает команды и пишет результат в лог.

## Admin roles
Админы задаются в .env через ADMIN_USER_IDS (список user_id через запятую).

Начиная с 2026-03-11 `admin_service` сам синхронизирует эти `ADMIN_USER_IDS` в таблицу `admin_users` при старте сервиса, если в БД уже есть хотя бы один пользователь. Для таких Telegram ID сервис автоматически:
- создаёт запись `admin_users`, если её нет;
- восстанавливает `is_active=true`, если аккаунт был деактивирован;
- гарантирует наличие роли как минимум `admin`.

Дополнительно ручки `/auth/auto-provision` и `/auth/one-time-link` теперь сами чинят потерянную связку `tg_user_id -> admin_user`, поэтому доступ в админку не должен «слетать» после рестартов или ручных правок БД.

## One chat - one active catalog
В одном чате может быть только один активный каталог (status=open).
Новый каталог создается только когда предыдущий закрыт.

## Commands

### Open catalog
- `/catalog_open [CODE]`
- `/open [CODE]`
Опционально можно добавить `| Title`:
`/catalog_open 20260112 | Murmansk batch`

Если CODE не указан - используется YYYYMMDD в UTC.

### Close catalog
- `/catalog_close`
- `/close`
- `/stop_all`

Переводит активный каталог в status=closed.

### Add / update catalog item
- `/item_add SKU | Title | unit=... | pack=... | price=...`

Пример:
`/item_add NERKA | Нерка | unit=kg | pack=1.2-1.8kg | price=1240 r/kg`

Повторный вызов с тем же SKU обновляет позицию.

### Stop item
- `/item_stop SKU`
Помечает позицию is_active=0 и проставляет stop_at.

## Web admin panel

Админ‑панель состоит из двух частей:

- `admin_service` (FastAPI) — аутентификация, роли, доступы.
- `admin-web` (React + MUI) — интерфейс управления.

### Основные операции

1) **Авторизация**: `HttpOnly` cookie session + one-time links из Telegram
2) **Каталоги**: создание, открытие/закрытие, CRUD товаров, стоп-лист, aliases
3) **Заказы**: просмотр, фильтрация, смена статуса, **Excel экспорт (XLSX, только owner + с password confirmation)**
4) **Настройки бота**: видимость бота (`bot_visible`), антиспам, тексты ответов, шаблоны и кнопки — в `Настройки → Бот`
5) **Admin-Chat scoping**: назначение админов к чатам (owner-only)
6) **Аналитика**: графики, топ-товары, статистика по точкам — только owner, и это проверяется backend-ом
7) **Owner Debug Mode**: owner включает debug-режим переключателем в `Settings`, после чего видит системную диагностику, project state и страницу `Debug`
8) **Integration API**: внешние сервисы подключаются через service-key ручки (`/integrations/*`)

### Создание каталога
- Чат выбирается из выпадающего списка доступных чатов (`GET /chats`).
- Новый чат появляется автоматически после события добавления бота в чат (`my_chat_member/chat_member`), без ручного INSERT в БД.
- Уникальный код каталога генерируется backend автоматически.
- Только owner может создавать каталоги.
- По умолчанию новый каталог создаётся **пустым**. Backend больше не подставляет товары из последнего каталога чата, если оператор явно не выбрал источник копирования.
- Если нужен перенос ассортимента, оператор использует clone-flow или передаёт явный `source_catalog_id`; неявного «скопировать последний каталог этого чата» больше нет.

### Импорт существующего каталога в другой чат
- На странице `Каталоги` доступна кнопка импорта/клонирования каталога в другой чат.
- Backend endpoint: `POST /catalogs/{catalog_id}/clone`
- В запросе указываются:
	- `target_chat_id` (Telegram chat id назначения),
	- `title` (опционально),
	- `close_existing_open` (опционально: закрыть текущий open-каталог в чате назначения).
- Используется для быстрого переноса одинакового ассортимента между городскими/региональными чатами.

### Создание каталога вставкой текста
- В раскрытом каталоге доступна кнопка **«Вставить текстом»**.
- Оператор вставляет список позиций построчно в том же виде, как он пришёл в исходном сообщении/прайсе.
- Backend endpoint: `POST /catalogs/{catalog_id}/import-text`
- Поведение:
	- каждая непустая строка становится отдельной позицией каталога;
	- порядок строк сохраняется 1-в-1 через `position_order`;
	- единица (`ШТ`, `КГ`, `УП`) определяется автоматически по хвосту строки;
	- существующие позиции каталога не стираются, новые добавляются в конец.
- После импорта UI автоматически запускает перепарсинг заказов по **текущему** каталогу, чтобы новые/обновлённые позиции сразу применились к уже сохранённым заказам.
- Важно: этот flow перепарсивает **заказы**, а не каталог. Клиентские
  `tg_updates` и тексты заказов никогда не достраивают каталог. Отдельное
  исключение — включённый sysadmin-флаг `feature_catalog_admin_post_sync`:
  подтверждённый admin/sender-chat список товаров является альтернативным
  operator-owned import flow (см. [[26-catalog-source-of-truth]]).

### Очистка каталога целиком
- В раскрытом каталоге owner может использовать кнопку **«Удалить всё из каталога»**.
- Backend endpoint: `DELETE /catalogs/{catalog_id}/items`
- Перед удалением сервис снимает связи `order_lines.catalog_item_id` у связанных строк, но не переписывает `orders.raw_text`, историю заказа или исходные строки.
- Видимость кнопки управляется sysadmin-toggle `feature_catalog_delete_all_items` в `Debug → Sysadmin → Каталог`.

### Excel экспорт (операционный)
- Кнопка «📥 Экспорт заказов» на странице заказов открывает диалог гибкого экспорта
- В диалоге можно выбрать: чат, раздачу, точку выдачи, статус, даты `от/до`, текстовый поиск
- Перед запуском выгрузки owner повторно вводит пароль; backend выдаёт краткоживущий step-up token и без него XLSX не отдаётся
- `GET /orders/export?...` → XLSX файл с выбранными фильтрами
- 4 листа: Заказы, Позиции, Сводка по товарам, По точкам
- Цветовое кодирование статусов
- В деталях заказа и в XLSX единицы выводятся в message/source-style формате (`КГ`, `Г`, `ШТ`, `УП`), чтобы оператор не видел служебные lower-case обозначения.
- Операционный экспорт автоматически исключает технические `rejected`-записи вида `message no longer qualifies as order` (не клиентские заказы).
- Если после ручного обновления каталога или изменения правил парсинга в диапазоне остаются старые `partial`, используйте `Debug → catalog-reprocess` для пересчёта заказов по актуальному каталогу. Этот инструмент не меняет каталог и не тянет позиции из `tg_updates`.

### Пагинация списка заказов (обновлено 2026-04-28)

- `OrdersPage` больше не угадывает число страниц по длине текущего ответа.
- `GET /orders` теперь отдаёт реальный total в header `X-Total-Count`, а UI строит пагинацию по фактическому количеству подходящих заказов.
- Технические `rejected`-записи без клиентских данных и с ошибкой `message no longer qualifies as order` исключаются **до** расчёта total и до применения `limit/offset`, чтобы страницы не выглядели «дырявыми» и старые заказы не сдвигались за невидимые служебные строки.
- В `OrdersPage` источник соцсети вынесен в отдельный фильтр-кнопки `Все / TG / MAX`; видимость управляется sysadmin-настройкой `orders_filter_show_source_provider`. Каталог выбирается отдельным фильтром `catalog_id`, не через сортировку.

### Экспорт истории (audit)
- В UI отдельная кнопка истории убрана, чтобы не перегружать основной флоу операторов.
- Backend endpoint `GET /orders/export-history?...` сохранён для audit / reconciliation сценариев и интеграций.
- Для вызова теперь тоже требуется password confirmation owner-а.
- `GET /orders/export-history?...` → XLSX файл с теми же фильтрами
- Листы:
	- `История заказов`
	- `История строк`
	- `Сводка аудита`

### Комплексный экспорт-конструктор (добавлено 2026-03-14)
- Отдельная страница **«📥 Экспорт данных»** в навигации (по умолчанию owner-only)
- 16 типов листов: справочники (каталоги, позиции, точки), статистика (по точкам, чатам, регионам, статусам), аналитика (по позициям, остаток vs забрано, топ товаров, точность парсера), выдача (выданные, оставшиеся, сводка), полные данные (все заказы, все строки)
- 5 шаблонов: полный отчёт, отчёт по выдаче, аналитика, дамп каталогов, полный дамп
- Фильтры: глобальные (каталог, чат, даты, имя файла) + per-sheet (catalog_id, даты, limit)
- Endpoints: `GET /exports/presets`, `POST /exports/build`
- Оба endpoint-а теперь защищены не только JWT, но и policy `owner only`; сама сборка дополнительно требует password confirmation.
- Frontend-контур экспорта работает по view-model паттерну (`useExportPageModel`) + изолированные UI-карточки (`TemplateExportCard`, `SheetSelectorCard`, `GlobalFiltersCard`, `SelectedSheetsCard`), чтобы изменения не превращали страницу в монолит.
- Если sysadmin-настройки экспорта временно недоступны (`getSettings`), страница использует безопасные значения по умолчанию и продолжает рендериться.
- Подробности: [[07-excel-export]]

### Режимы работы бота в чате
- `PATCH /chats/{tg_chat_id}` с `{ "bot_visible": "inactive" | "hidden" | "reactions_only" | "full" }`
- `inactive`: бот полностью игнорирует чат — не читает новые сообщения, не создаёт заказы, не отвечает
- `hidden`: бот читает и обрабатывает, но не пишет сообщения и не ставит реакции
- `reactions_only`: ставит реакции и пишет только ошибки
- `full`: обычный рабочий режим
- Практический смысл:
	- `hidden` — stealth/тихое наблюдение
	- `inactive` — операционная пауза без удаления бота из чата

### Конструктор поведения бота в админке
- `Настройки → Бот` теперь управляет не только общими переключателями, но и почти всем user-facing UX бота.
- Owner может менять:
	- тексты `/start`, `/menu`, `/help`, `/order_template`, `/order_example`, `/order_rules`;
	- тексты профиля пользователя и служебных подсказок;
	- сообщения об отсутствии активной раздачи, дозаказе, невозможности написать в личку и т.п.;
	- состав и подписи inline-кнопок пользовательского меню;
	- видимость admin-only кнопок (`Админ-панель`, `Команды`).
- Поддерживаются плейсхолдеры в шаблонах, например:
	- `{pickup_points}`
	- `{pickup_example}`
	- `{pickup_bullets}`
	- `{admin_extra}` / `{admin_commands}`
	- `{url}`
	- `{profile_name}`, `{profile_phone}`, `{profile_pickup}`
- Ниже этих настроек есть **live preview**, где можно:
	- выбрать сценарий сообщения,
	- выбрать чат для подстановки точек выдачи,
	- переключить режим “как пользователь / как админ”,
	- сразу увидеть текст и inline-кнопки без сохранения и ручной проверки в Telegram.

### Авто-обнаружение точек выдачи по чатам
- При обработке заказов бот автоматически добавляет новые точки выдачи в `pickup_places` для конкретного чата.
- Эти точки сразу попадают в шаблоны `/order_template`, `/order_example`, `/help` этого же чата.
- Таким образом примеры в чате и админке отражают реальные точки из живых сообщений пользователей.

### Owner Debug Mode
- Новая роль **не создаётся** — используется owner-only toggle `owner_debug_mode` в `bot_settings`
- При выключенном debug mode owner видит обычный чистый UI без системных деталей
- При включенном debug mode появляются:
	- страница `Debug`
	- project state в `Settings`
	- системные признаки: schema/migrations, worker queue, webhook status, readiness по чатам

### Единая команда обслуживания
- `make sync` — build + migrations + force-recreate stack
- Рекомендуется после `git pull`, миграций и infra/ui/backend изменений

### POST preflight перед risky изменениями
- Для изменений в `login/auth/cookie/CSRF/middleware` и mutating endpoint-ах перед завершением задачи обязательно запускать:
	- `make check-post-preflight`
- Команда прогоняет целевой startup/auth/csrf regression smoke и ловит типичные падения POST-контракта до деплоя.

### Catalogs preflight перед risky изменениями (добавлено 2026-04-17)
- Для изменений в `admin_service/app/api/routers/catalogs.py`, `core_tables` и schema-совместимости `chats/catalogs/catalog_items` перед завершением задачи обязательно запускать:
	- `make check-catalogs-preflight`
- Команда прогоняет py_compile + regression тесты legacy-schema для `GET /catalogs` и `GET /catalogs/{id}/items`.

### Обязательный prebuild guard
- Перед `make compose-build`, `make compose-restart`, `make sync` сначала запускать:
	- `make check-prebuild`
- `check-prebuild` = `check-post-preflight` + `check-catalogs-preflight`; если guard не проходит, билд/рестарт не выполняется.

### Опциональные вкладки «Проблемы» (обновлено 2026-04-14)

- Вкладка «Проблемы» в разделе **Заказы** управляется отдельно через sysadmin-toggle `orders_show_problems_tab`.
- Вкладка «Проблемы» в разделе **Выдача** управляется отдельным toggle `delivery_show_problems_tab`.
- Эти переключатели независимы: можно оставить проблемы в заказах, но скрыть их в выдаче (или наоборот).

### Integration API (внешние сервисы)
- Аутентификация: `X-Service-Key` (значение из `ADMIN_INTEGRATION_SERVICE_KEY`)
- Основные ручки:
	- `GET /integrations/capabilities`
	- `GET /integrations/chats`
	- `GET /integrations/catalogs/open`
	- `GET /integrations/pickup-places`
	- `GET /integrations/orders`
- Детали: [[13-integration-api]]

### One-time login links

- Выдаются ручками `POST /auth/one-time-link` и `POST /auth/auto-provision`
- Для их выдачи используется только `ADMIN_ONE_TIME_KEY`
- Ссылка теперь имеет вид:
	- `/auth-callback#one_time_token=...`
- Почему так:
	- token не попадает в обычные серверные access logs как query string
	- token серверно помечается как consumed после первого успешного `POST /auth/token-login`

## Notes
- Каталог в рамках раздачи не дополняется новыми товарами от пользователей. Только по команде админов.
- Парсинг прайса из “красивых сообщений” и ответы бота в чат - следующий этап.
## Distribution Mode (режим выдачи, обновлено 2026-07-15)

- Настройки в `Settings` → вкладка «Точки»:
	- `distribution_mode` — глобальный рубильник,
	- `distribution_mode_chat_ids` — список выбранных чатов/городов, где режим должен действовать,
	- `distribution_message` — кастомный текст ответа бота.
- Когда режим включён глобально или для конкретного чата: worker отклоняет все **новые** заказы и отвечает настроенным сообщением о завершении сбора.
- Существующие заказы и сценарии выдачи не блокируются.
- Подходит для сценария: каталог ещё нужен для просмотра, но приём новых заказов в конкретных городах уже остановлен.

## Telegram Deep Link в карточке заказа (добавлено 2026-07-15)

- В детальной карточке заказа в админке появилась кнопка «Открыть в Telegram».
- Ссылка формата `https://t.me/c/{chat_id}/{message_id}` (для supergroup чатов автоматически обрезается префикс `-100`).
- Позволяет быстро перейти к исходному сообщению для контекста.

## Редактирование пользователем исходного сообщения заказа (обновлено 2026-03-16)

- Если пользователь редактирует сообщение **до начала выдачи**, worker перепарсивает тот же заказ по `source_message_id` и обновляет его содержимое.
- Если после редактирования товары больше не распознаются, исходный заказ отменяется со статусом `canceled` и пометкой `edited: no catalog match`.
- Если по заказу уже есть `delivery_status` (выдача началась, зафиксирована или завершена), worker **не переписывает состав автоматически**, чтобы не ломать операционный контур выдачи.
- В этом случае в историю сохраняется новый `raw_text`, а пользователю отправляется сообщение, что дальнейшие правки нужно решать через оператора.

## Обратная связь по стоп-товарам (добавлено 2026-07-15)

- Бот теперь при отклонении заказа показывает **причину стопа** для каждого товара:
  - «🛑 стоп (причина)» — если у товара задан `stop_reason`
  - «🛑 стоп» — если причина не указана
- Пользователь сразу понимает, почему конкретный товар не принят, и может скорректировать заказ.

## Навигация и управление точками выдачи (обновлено 2026-07-15)

- Основной раздел переименован в **«Админы точек»**.
- Управление точками выдачи вынесено туда же: на странице доступны и назначения админов, и CRUD самих точек.
- Во вкладке `Settings → Точки` остаётся связанная конфигурация и резервное редактирование точек, но основной operational flow теперь в одном месте.
- Справочный контекст по ролям перенесён в `Settings → Доступ`.
- Settings по-прежнему поддерживает deep link через query-параметр `?tab=N`.

## Настройки: новая структура (обновлено 2026-04-07)

- `Настройки → Приложение` — owner-mode, общие параметры админки и структура экранов.
- `Настройки → Бот` — ответы, уведомления, видимость бота в чатах и антиспам.
- `Настройки → Точки` — точки выдачи и режим «сбор завершён / выдача».
- `Настройки → Интерфейс` — темы оформления.
- `Настройки → Доступ` — роли команды + section visibility с пояснениями по новой роли-модели.

## Mobile UX админки (обновлено 2026-03-14)

- На телефонах админка теперь использует **нижнюю быструю навигацию** по главным разделам вместо сценария “открывай drawer на каждый клик”.
- В верхней панели показывается **название текущего раздела**, чтобы при переходах и deep-link сценариях было видно контекст.
- `Заказы` на мобильных показываются **карточками**, где сразу видны:
	- номер заказа,
	- клиент,
	- точка выдачи,
	- статус,
	- статус выдачи,
	- проблемы,
	- быстрые действия `Подробнее / Изменить / Удалить`.
- Эти карточки теперь собраны в более **спокойный compact layout**: ключевые поля сгруппированы в mini-info блоки, а не разбросаны по множеству мелких chip-ов, поэтому список лучше читается в Telegram browser и на узких Android-экранах.
- `Выдача заказов` на мобильных тоже работает через **карточные списки** во всех трёх вкладках (`К выдаче`, `Отмеченные`, `Проблемы`), чтобы оператору не приходилось скроллить таблицу в две стороны.
- В `Выдача заказов` сверху теперь не висят большие dashboard-карточки: оператор видит **вкладки + фильтр + компактную мини-сводку**, а значит очередь начинается заметно выше и не требует лишнего скролла.
- В мобильных карточках выдачи скрываются пустые / неинформативные значения, поэтому UI не засыпает оператора прочерками без контекста.
- Карточки `Выдачи` на телефоне теперь собраны по тому же паттерну, что и `Заказы`: сверху короткий identity-блок, затем mini-info cards для телефона/статуса/времени и уже ниже действия. Это уменьшает визуальный шум и делает список стабильнее в Telegram browser.
- Основные рабочие диалоги (`детали заказа`, `экспорт`, `выдача`, `редактирование проблемного заказа`, `добавление точки`) на телефоне открываются в **full-screen** режиме.
- Дополнительно страницы `Пользователи`, `Админы точек` и `Каталоги` на телефоне переключены на **card-based layout** вместо широких таблиц.
- В `Каталогах` мобильные карточки и раскрытые товары тоже уплотнены: метаданные каталога и товара показываются через компактные info-блоки, а массовые chip-ленты заменены на более читаемые мини-секции.
- В `Пользователях` мобильные карточки теперь лучше разделяют identity, роли, служебные метаданные и admin-actions: меньше “всё в одну кучу”, удобнее читать список и проще попадать по действиям.
- В `Админах точек` карточки назначений и точек выдачи тоже собраны в mini-info blocks, чтобы связи “кто ↔ какие точки” считывались быстрее, а включение/удаление точки не выглядело как набор случайных контролов.
- В `Настройки` на мобильных вкладки заменяются на **селектор разделов**, а кнопка `Сохранить` закреплена снизу экрана, чтобы owner мог менять конфиг одной рукой.
- В `Настройки → Интерфейс` появился стиль **`Минималистичный`**: его можно включить для более воздушной mobile-подачи и так же быстро отключить обратно.
- Для Telegram browser улучшены **safe-area отступы**, верхняя панель и нижняя навигация, чтобы интерфейс меньше упирался в системные зоны и выглядел стабильнее на узких экранах.
- Дополнительно выровнен **единый mobile spacing rhythm**: внешний отступ экрана, внутренние паддинги карточек, диалогов и action-footer-ов теперь согласованы между разделами, чтобы UI не “скакал” по плотности при переходе со страницы на страницу.
- Раздел `Заказы` не управляет выдачей: статусы выдачи там только отображаются для контекста, а все операционные действия выполняются в `Выдача заказов`.
- В детальной карточке заказа на телефоне customer/meta блоки и нижние действия тоже уплотнены под one-hand usage: меньше лишнего воздуха, лучшее распределение ширины и более предсказуемое поведение full-screen диалога.
- Full-screen диалоги в `Выдаче` и `Каталогах` теперь используют более предсказуемый mobile action-footer: главная кнопка и отмена не скукоживаются в одну строку, а нормально раскладываются под палец.
- Те же mobile action-footers теперь приведены к общему виду и в `Пользователях`/`Админах точек`, чтобы добавление, редактирование, сброс пароля и назначения не меняли поведение футера от страницы к странице.

## Delivery Management (добавлено 2026-07)

### Роли
- **owner**: полный доступ, включая шаблоны, темы, системные настройки и состав ролей.
- **regional_admin**: локальный супервайзер; role card отображается отдельно от owner и старых legacy-ролей. Управляет только теми менеджерами и операторами, у которых есть пересечение по назначенным городам / регионам.
- **manager**: работает только с заказами, ошибками, карточкой заказа и корректировками данных.
- **pickup_admin**: оператор выдачи. Может отмечать выдачу только на назначенных точках.
- Legacy-роли `admin` и `viewer` не используются в новых настройках: `admin` трактуется как совместимый менеджер, `viewer` скрыт из назначения.

### Users / регионы

- `UsersPage` теперь показывает отдельную колонку **«Города / регионы»**.
- Owner может назначать города любым рабочим ролям, а `regional_admin` — только в рамках собственных регионов и только для менеджеров / операторов в своей зоне.
- При создании нового пользователя `regional_admin` может оставить регионы пустыми: тогда backend автоматически назначит ему те же города, что и у текущего регионального администратора.

### Флоу выдачи заказов
1. Owner назначает pickup_admin на точку через «Админы точек» (`/pickup-admin`).
2. Pickup admin теперь попадает сразу в operational section, а не на owner-dashboard.
3. Раздел «Выдача заказов» (`/delivery`) теперь работает как **рабочее место смены** и содержит 3 вкладки:
	- **К выдаче**: активная очередь заказов по точкам, с быстрыми действиями «полностью / частично / передан / не выдан»
	- **Отмеченные**: единый журнал всех записей о выдаче, включая состав, исходный текст и действия по редактированию/откату
	- **Ошибки**: заказы со статусом `needs_admin` или строками `unknown_item`/`bad_qty`/`stopped`
4. На мобильном `pickup_admin` сначала видит именно **рабочую очередь**, а не растянутый статистический блок; summary сведена к компактным chip-метрикам.
5. При выдаче открывается модалка, где указывается статус, имя и телефон получателя, заметки, а по каждой строке можно разнести «выдано» и «осталось».
6. Для частичной выдачи теперь можно добавить **ручные позиции / пометки**, если фактическая выдача не совпадает один в один с исходным составом заказа. Поле выбора подсказывает позиции из **текущего заказа и текущего каталога/раздачи**, но при необходимости позволяет ввести свободную служебную пометку.
7. Для частичной выдачи или передачи можно указать данные другого получателя / того, кто заберёт остаток.
8. Если выбран статус `Передан другому лицу`, система теперь требует внести **новые данные получателя**; без них запись не сохранится.
9. Если выбран статус `Не выдан`, система фиксирует отдельную запись в журнале и рекомендует указать причину в заметках, чтобы следующая смена видела контекст.
10. Если выдача была отмечена по ошибке, оператор может выполнить **откат выдачи** прямо из журнала; backend удалит запись выдачи и пересчитает `delivery_status` заказа.
11. В разделе `Заказы` pickup-admin видит только заказы своих точек; это ограничение также enforced на backend для списка, карточки, PATCH и XLSX-экспорта.
12. Quick-actions в карточке заказа теперь работают и для `needs_admin` / `partial`, но статус `Передан` не выставляется в один клик — для него оператор открывает полноценный delivery flow и вводит новые данные получателя.

### Parser edge case

- Сообщения формата `Елена 43 80 ...` теперь корректно интерпретируются как телефон `4380`, а не как разрозненные числа в имени.

### Экспорт по шаблону для выдачи

- `GET /orders/export-template` формирует **один рабочий лист** без лишних страниц из загруженного шаблона.
- Docker runtime сервиса теперь тоже содержит дефолтный шаблон (`samples/excel/template.xlsx`), поэтому endpoint одинаково работает и локально, и в контейнере.
- В шаблон, помимо строк заказа, могут подставляться служебные данные по выдаче:
  - статус заказа,
  - статус выдачи,
  - получатель,
  - что выдано,
  - что осталось,
  - заметки,
  - ссылка на исходное Telegram-сообщение.
- Если такие заголовки уже есть в шаблоне — данные попадут в них; если нет, сервис добавит колонки автоматически справа.

### API эндпоинты (admin_service)
- `GET /deliveries` — список записей выдачи (с пагинацией)
- `POST /deliveries` — создать запись о выдаче
- `GET /deliveries/{id}` — детали выдачи
- `PATCH /deliveries/{id}` — обновить выдачу
- `DELETE /deliveries/{id}` — отменить выдачу и вернуть заказ в рабочий поток
- `GET /orders/delivered` — выданные заказы
- `GET /orders/errors` — ошибочные заказы
- `GET /pickup-admin-assignments` — назначения админов на точки
- `POST /pickup-admin-assignments` — назначить админа на точку
- `DELETE /pickup-admin-assignments/{admin_user_id}/{pickup_place_id}` — удалить назначение
- `GET /pickup-admin/my-points` — мои точки (для pickup_admin)
