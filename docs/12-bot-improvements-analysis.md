# Анализ улучшений бота (без фанатизма)

Дата: 2026-01-22

Эта заметка фиксирует, что в боте уже есть, что «криво/косо» с точки зрения UX/качества обработки сообщений, и какие улучшения можно сделать, чтобы бот стал «крутым умным админом» — но без превращения в LLM-комбайн.

## 0) Контракт: каким хотим видеть бота

**Вход:** сообщения из Telegram-чата (group/supergroup/private), включая `edited_message` и callback-кнопки.

**Выход:**
- для пользователя — короткий, понятный ответ (принял/частично/не принял + что сделать)
- для админа — управляемость (каталог/стопы/экспорт/аналитика), минимум ручной рутины
- для системы — устойчивость (идемпотентность, не дублировать вклад сообщений)

**Принципы:**
- быстро и детерминированно по умолчанию (regex/эвристики)
- «умность» подключать точечно (suggestions, авто-уточняющие вопросы, подсказки по формату)
- не отвечать на всё подряд (чтобы не раздражать чат)

## 1) Что уже сделано (опорные точки)

Согласно текущим docs и коду:
- Архитектура `webhook -> tg_updates -> worker` обеспечивает устойчивость и идемпотентность.
- Есть парсинг заказа, статусы строк (`ok/stopped/unknown_item/bad_qty`) и статусы заказа (`active/partial/rejected/needs_admin`).
- Есть профили пользователя (`/set_pickup`, `/set_phone`) для автозаполнения.
- Есть inline-кнопки пользователя (`public:/...`) и router callback’ов.
- Есть auto-unstop по `stop_until`.
- Есть админ-панель (UI+API) для управления каталогами/товарами/ролями.

Это хорошая основа: «накрутка умности» должна идти поверх неё.

## 2) Где бот пока «кривой-косой» (симптомы и причины)

### 2.1 UX в чате
**Симптомы:**
- пользователю непонятно, что именно не так; мало «следующего шага»
- ответы иногда слишком общие; не хватает точного подсвечивания ошибок
- кнопки/команды есть, но flow не «ведёт» пользователя

**Причины:**
- ответ формируется по статусам, но не всегда добавляет контекст (какое поле отсутствует, пример, быстрый action)
- некоторые edge-cases распознавания «похожести на заказ» всё ещё могут дырявить UX

### 2.2 Качество распознавания позиций
**Симптомы:**
- `unknown_item`: пользователь пишет чуть иначе, чем каталог
- `bad_qty`: разные форматы «2×250г», «полпачки», «1кг200»

**Причины:**
- алиасы в `CatalogItem.aliases` пока не используются как «богатый словарь» (скорее строка)
- не хватает нормализации/токенизации внешней формы названия

### 2.3 Управляемость админом
**Симптомы:**
- админ вынужден «вручную дописывать каталог» из чата
- нет «умной подсказки» для админа: какие товары чаще всего не распознаны, какие точки выдачи люди пишут криво

**Причины:**
- аналитика есть, но мало operational-метрик качества парсинга
- нет отдельного «Quality dashboard» для админа

## 3) Улучшения: короткий список по приоритету

### A. Быстрые wins (1–2 дня)

1) **Улучшить тексты ошибок (user-facing)**
- для `bad_qty`: показывать 1–2 примера формата именно по этой строке
- для `unknown_item`: показывать top-2 suggestion (уже частично есть `_collect_suggestions`) + кнопка «показать шаблон»
- для missing полей: уже есть `_build_missing_keyboard`, но стоит добавлять пример ввода сразу в ответ

2) **Нормализация названий товаров (без AI)**
- привести к lower, убрать лишние символы, заменить `ё->е`, схлопнуть пробелы
- поддержать простые синонимы уровня «филе/филешка», «креветка/креветки» через pre-processing

3) **Подсказка точки выдачи**
- сейчас есть список `pickup_places`. Можно:
  - при нераспознанной точке показывать 3 ближайших по совпадению (like items suggestions)
  - предложить кнопки выбора, если точек немного (<=6)

4) **Стабильное поведение в DM/Group**
- сделать явную политику: если `reply_mode=dm`, то **в чате минимальный “я ответил в личку”** и никогда не спамить деталями

### B. «Умный админ» без фанатизма (3–7 дней)

5) **Quality metrics + отчёт админам (в UI)**
- добавить агрегаты:
  - доля `unknown_item` по каталогу
  - топ-10 нераспознанных названий (normalized)
  - топ-10 `bad_qty` примеров
  - топ-10 «кривых» точек выдачи

6) **Полуавтоматическое пополнение алиасов**
- в admin UI: кнопка «добавить алиас» прямо из списка unknown-item примеров
- хранить алиасы не одной строкой, а JSON/таблицей (если захотим качественно)

7) **Авто-драфт для админа**
- если неизвестный товар повторяется N раз за сутки → предложить админам создать `CatalogItem` в статусе `draft` (или inactive)

### C. Осторожное применение LLM (опционально)

8) **LLM только для “edge” сообщений**
- если эвристики не уверены або слишком много `unknown_item/bad_qty`
- LLM должен возвращать **структуру**, не «текстовую болтовню»
- при недоступности LLM — graceful degradation

Важно: LLM не должен решать за пользователя; максимум — предложить варианты.

## 4) Edge cases, которые стоит закрыть

- edited_message: пересчёт без дублей (в целом заложено) — добавить тесты/лог-метрики на дубли
- спам/медиа/длинные тексты: не отвечать или отвечать только на явные команды
- 2×250г, 3*0.5кг, 10шт по весовому товару — нормализатор qty
- «пункт выдачи» в произвольной форме (опечатки) — suggestions

## 5) Рекомендованный план следующими шагами

1) Добавить «quality dashboard» (пара эндпоинтов в admin_service + виджет в admin-web).
2) Сделать нормализацию товаров + suggestions более агрессивными.
3) Сделать suggestions для pickup place.
4) Опционально: мини-wizard через callback’и только для missing полей (name/phone/pickup).
