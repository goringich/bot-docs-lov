# Microservices Architecture (v2)

Этот документ описывает целевую микросервисную архитектуру системы и разделение зон ответственности между сервисами.

## 🎯 Цели

- Чёткое разделение ответственности между сервисами
- Независимые релизы и масштабирование
- Прозрачные контракты между компонентами
- Минимизация кросс‑сервисных зависимостей

## 🧩 Сервисы и ответственности

### 1) `backend` (Telegram API + Order Engine)
**Роль:** входящий шлюз Telegram + бизнес‑логика заказов.

**Зоны ответственности:**
- Приём webhook updates от Telegram
- Валидация и запись raw updates в БД
- Основная обработка заказов (парсинг, агрегация, остановки)
- Команды админа в Telegram
- Экспорт Excel

**События/контракты:**
- HTTP webhook `/telegram/webhook`
- Локальная очередь в БД `tg_updates`

---

### 2) `worker` (Update Processor)
**Роль:** асинхронный процессор обновлений.

**Зоны ответственности:**
- Чтение `tg_updates`
- Идемпотентная обработка сообщений
- Вызов `order_domain` + `order_service`
- Отправка ответа пользователю

**Контракты:**
- Таблицы `tg_updates`, `message_snapshots`, `orders`, `order_lines`

---

### 3) `admin_service` (RBAC API)
**Роль:** административный REST API для UI.

**Зоны ответственности:**
- JWT‑аутентификация
- Управление пользователями и ролями
- Чтение/фильтрация заказов
- Управление настройками бота (через `bot_settings`)
- CRUD точек выдачи

**Контракты:**
- REST API `GET/POST /settings`, `GET/POST/PATCH/DELETE /pickup-places`

---

### 4) `admin-web` (React UI)
**Роль:** web‑панель админов и аналитики.

**Зоны ответственности:**
- UI управления заказами
- Настройки бота
- Аналитика и графики
- Экспорт CSV

---

### 5) `analytics` (планируется)
**Роль:** агрегированные метрики и отчёты.

**Зоны ответственности:**
- Периодические агрегации (daily/hourly)
- Подготовка данных для графиков
- Хранение снепшотов аналитики

---

## 📦 Контракты данных (ownership)

| Таблица | Владелец сервиса | Назначение |
|--------|------------------|-----------|
| `tg_updates` | `backend` | очередь Telegram updates |
| `message_snapshots` | `worker` | снимки сообщений |
| `orders`, `order_lines` | `worker` | заказы и строки |
| `bot_settings` | `admin_service` | настройки бота |
| `pickup_places` | `admin_service` | точки выдачи |

## ✅ Рекомендации по развитию

1. **Выделить API слой в `admin_service`** (модуль `app/api/v1/`)
2. **Формализовать DTO‑модели** в `schemas.py` для всех новых эндпоинтов
3. **Вынести экспорт Excel в сервис `exporter`** (опционально)
4. **Добавить `analytics` сервис** при росте нагрузки

## 🔐 Безопасность

- Внешний доступ только через `admin_service` и `backend`
- Все внутренние сервисы общаются через приватную сеть Docker
- JWT токены только для admin UI

## 📌 Итог

Текущая архитектура уже близка к микросервисной, ключевая задача — формализовать границы и контракты, чтобы каждый сервис можно было развивать независимо.
