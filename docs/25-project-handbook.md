# Project Handbook

Этот документ — основной высокий уровень по всему проекту. Его задача не заменить все частные документы, а собрать систему в одну сквозную картину: что это за продукт, из каких частей он состоит, как течёт информация, кто чем пользуется, где лежат границы ответственности и куда идти за деталями.

## 1. Назначение проекта

`otlichniy-ulov` — это прикладная система обработки заказов, которая выросла из Telegram-бота, но уже давно не ограничивается только Telegram-сценарием.

Система решает несколько задач одновременно:

- принимает сообщения из чатов и превращает их в структурированные заказы;
- хранит каталог товаров, точки выдачи, статусы заказов и журнал изменений;
- даёт операционной команде web-админку для модерации, выдачи, выгрузок и управления доступами;
- предоставляет API и bridge-контур для интеграций и будущих не-Telegram провайдеров;
- формирует экспортные представления, включая шаблонные XLSX-файлы под реальную раздачу.

На практике это означает, что Telegram здесь больше не является «самим продуктом». Telegram — лишь один из transport-слоёв, а ядро проекта живёт в доменной модели заказа, worker-пайплайне, административном API и операционной админке.

## 2. Что входит в систему

Проект состоит из нескольких основных частей:

### `backend/`

Основной bot/backend-контур:

- webhook ingress для входящих Telegram update-ов;
- `worker.py`, который разбирает update-ы и решает, что с ними делать;
- доменная логика парсинга заказов;
- запись и пересчёт заказов;
- отправка ответов обратно в чат;
- хранение и обработка message snapshots, edited messages, отмен, до-заказов и служебных событий.

### `admin_service/`

Отдельный сервис административного API:

- аутентификация и роли;
- CRUD для пользователей, каталогов, товаров и точек выдачи;
- API заказов, аналитики, выдачи и экспортов;
- password-confirmed операции для чувствительных действий;
- security и audit-поведение для web-контура.

### `admin-web/`

Фронтенд операционной админки:

- работа с заказами и фильтрами;
- работа с выдачей;
- каталоги и пользователи;
- запуск экспортов;
- настройки интерфейса и role-aware UI;
- sysadmin / observability сценарии.

### `docs/`

Документация проекта:

- handbook, runbook, reference, integration docs;
- changelog и historical context;
- API handbooks и operational guides.

### `samples/`

Реальные и тестовые артефакты:

- Excel-шаблоны;
- Telegram exports;
- эталонные форматы для проверки парсера и экспортов.

### `scripts/`

Сервисные сценарии:

- запуск и smoke-checks;
- maintenance и генерация артефактов;
- локальная диагностика и вспомогательные automation flow.

### `infra/`

Инфраструктурные файлы и docker-related обвязка.

## 3. Бизнес-сущности проекта

Ключевые сущности домена:

- чат;
- входящее сообщение / update;
- заказ;
- строка заказа;
- каталог;
- товар каталога;
- точка выдачи;
- пользователь админки;
- роль пользователя;
- событие выдачи;
- экспортный набор данных.

На уровне продукта всё крутится вокруг одной центральной задачи: из шумного человеческого текста получить корректный структурированный заказ, который потом можно обработать, выдать и выгрузить в нужном формате без потери контекста.

Подробная модель лежит в [[04-data-model]], но важно понимать общую иерархию:

1. transport приносит raw message;
2. система сохраняет update и snapshot;
3. parser/worker пытается понять, является ли сообщение заказом;
4. если да, создаётся или пересчитывается order + order_lines;
5. дальше заказ живёт в операционном контуре: фильтры, статусы, выдача, экспорт, отмены, аналитика.

## 4. Главная архитектурная идея

В проекте важно разделение на четыре слоя:

1. transport ingestion
2. orchestration / worker pipeline
3. domain logic
4. operational admin surface

### Transport ingestion

Это слой, который принимает update от Telegram или другого провайдера. Его задача — надёжно принять событие, привести его к рабочему envelope и не потерять первичный raw context.

### Orchestration / worker pipeline

Это центральный слой принятия решений. Именно здесь определяется:

- это новый заказ или нет;
- это edited message или обычное сообщение;
- это отмена, до-заказ или шум;
- нужно ли пересчитать existing order;
- нужно ли ответить в чат;
- нужно ли обновить raw_text и агрегаты.

### Domain logic

Здесь живёт бизнес-смысл:

- как распознаётся товарная строка;
- как определяется количество;
- как отделяются имя, телефон, комментарий, точка выдачи;
- как считаются line items;
- как выглядят инварианты корректного заказа.

### Operational admin surface

Это admin_service + admin-web. Этот слой нужен не для парсинга, а для управляемости системы:

- просмотр и фильтрация;
- правки статусов;
- выдача;
- экспорт;
- роли и безопасность;
- работа с каталогом.

## 5. Сквозной поток данных

Ниже основной happy path.

### 5.1. Новый заказ из чата

1. Пользователь пишет сообщение в чат.
2. Telegram присылает update в backend webhook.
3. Update сохраняется и попадает в worker.
4. Worker определяет тип события.
5. Если сообщение похоже на заказ, вызывается parser/domain logic.
6. Parser выделяет позиции, количества, точку выдачи и метаданные.
7. Создаётся order и order_lines.
8. Бот отвечает пользователю по configured response mode.
9. Заказ становится виден в admin-web и доступен для дальнейшей обработки.

### 5.2. Редактирование сообщения

1. Пользователь редактирует исходное сообщение.
2. В систему приходит edited update.
3. Worker находит исходный заказ по message linkage.
4. Order пересчитывается заново из нового текста.
5. Система обновляет строки заказа и служебные поля.
6. Ответ в чат корректируется, если это предусмотрено flow.

### 5.3. Отмена заказа

1. Пользователь или администратор инициирует отмену.
2. Order меняет статус на canceled.
3. В raw representation сохраняется исходный текст заказа и ниже текст отмены.
4. Это позволяет видеть не только итоговый статус, но и полный audit trail на уровне сообщения.

### 5.4. Выдача

1. Оператор открывает `DeliveryPage`.
2. Видит очередь по точке выдачи.
3. Отмечает заказ выданным.
4. Система пишет событие выдачи.
5. При необходимости выдачу можно откатить, и заказ возвращается в рабочую очередь.

### 5.5. Экспорт

1. Пользователь в админке выбирает режим выгрузки.
2. admin_service строит нужный набор данных.
3. Формируется CSV/XLSX или шаблонная Excel-структура.
4. Если это чувствительный экспорт, применяется password-confirmation policy.
5. Файл используется как operational artifact для раздачи, сверки или внешнего обмена.

## 6. Парсер как ядро продукта

Parser — один из самых чувствительных участков системы, потому что именно он определяет, какое сообщение превратится в заказ, а какое будет отброшено как шум.

Основные требования к парсеру:

- не быть завязанным на костыли под конкретные позиции;
- опираться на каталог как на source of truth;
- корректно выделять quantity + product + pickup/meta;
- не принимать отзывы, обсуждения, рецепты и бытовой шум за заказ;
- уметь пересчитывать edited messages и до-заказы;
- сохранять объяснимость результата.

В проекте важно различать:

- «правильный заказ, который обязан парситься»;
- «похожее сообщение, которое не является заказом»;
- «частично понятный заказ, который требует осторожного поведения».

Детали логики и примеры форматов лежат в [[05-parsing-rules]].

## 7. Каталог как источник правды

Каталог — это не просто список для UI. Это operational source of truth для распознавания товара.

Из этого следуют важные последствия:

- новые товары должны попадать в каталог, а не вшиваться в parser keyword hacks;
- распознавание товара должно опираться на активный каталог чата/контекста;
- экспорт и выдача обязаны использовать те же товарные имена и структуры, что и каталог;
- источником истины является именно вставленный оператором текст каталога, из которого создаются `catalog_items`; каталог нельзя «подправлять под заказ» задним числом, кроме ручного добавления алиасов;
- шаблонные Excel-выгрузки должны быть совместимы с реальным operational naming, а не со случайной нормализацией.

Если каталог неактуален, начинают страдать сразу три контура:

- parser;
- admin filtering/analytics;
- exports.

## 8. Роли и операционная модель

В проекте есть role-aware административный контур. Даже если конкретный набор ролей эволюционирует, архитектурный смысл остаётся одинаковым:

- `owner` управляет всей системой и чувствительными действиями;
- `regional_admin` и смежные роли видят ограниченный по области контур;
- `pickup_admin` работает с выдачей и своей зоной ответственности;
- `sysadmin` нужен для технического наблюдения, debug и observability функций.

Ролевая модель влияет на:

- доступные разделы UI;
- доступность аналитики;
- доступность экспортов;
- возможность править пользователей и чувствительные настройки;
- видимость системных диагностических разделов.

Подробно это описано в [[12-admin-panel]] и [[11-security]].

## 9. Admin-web как рабочий инструмент

`admin-web` не является «витриной». Это основной operational cockpit.

Через него выполняются реальные рабочие действия:

- поиск и фильтрация заказов;
- изменение статусов;
- запуск экспортов;
- управление выдачей;
- поддержание каталога;
- администрирование пользователей;
- работа с настройками и техническими разделами.

Это означает, что любая backend-логика, которая влияет на видимость, безопасность или экспортный формат, должна оцениваться с точки зрения того, как это увидит оператор в админке.

## 10. Экспортный контур

Экспорт в этом проекте — не побочная функция, а полноценный operational output.

Есть несколько классов экспортов:

- табличные выгрузки для анализа и обмена;
- шаблонные XLSX-выгрузки в фиксированном формате;
- выгрузки под конкретную раздачу;
- конструктор экспортов под разные operational сценарии.

Особенно важно, что шаблонные Excel-экспорты должны быть совместимы с фактическим рабочим шаблоном `1 в 1`, а не просто «похожими».

При этом сам Excel-шаблон не становится новым source of truth: если строка export уже привязана к каталожному SKU / `catalog_item`, единицы и количество должны следовать каталогу, а не тексту сообщения пользователя и не числовым кускам в названии/заголовке вроде `125ГР` или `1200 Г`.

Детальный разбор лежит в [[07-excel-export]].

## 11. Интеграционный контур

Проект уже проектируется как transport-agnostic платформа. Это значит:

- Telegram — только один provider;
- можно добавлять bridge и новые источники событий;
- ядро не должно жёстко зависеть от конкретного мессенджера;
- интеграции должны работать через понятные контракты и capability profile.

Интеграционный слой включает:

- внешние API;
- provider bridge;
- auth и integration keys;
- messenger-agnostic contracts;
- будущие mobile / matrix / other provider use cases.

## 12. Безопасность

Ключевые security-принципы проекта:

- data-rich действия не должны оставаться в чат-контуре;
- чувствительные экспорты требуют усиленного подтверждения;
- аналитика и системные действия режутся backend-ролями, а не только UI;
- role model и audit trail важнее «удобства любой ценой»;
- integration access должен быть отделён от human admin access.

Практически это выражается в следующем:

- критичные действия уводятся в `admin_service` / `admin-web`;
- бот не должен быть боковым каналом утечки данных;
- owner-only и sysadmin-only функции должны контролироваться сервером;
- raw data, exporter и auth-layer должны согласованно соблюдать policy.

Подробности: [[11-security]] и [[24-admin-auth-and-integration-security-runbook]].

## 13. Тестирование и качество

Проект нельзя считать надёжным только потому, что «бот ответил в чате». Нужны несколько уровней проверки.

### Parser regression

Самая важная часть: реальные текстовые кейсы, проблемные сообщения, ложные срабатывания, edited message scenarios, отмены, до-заказы.

### API and admin tests

Покрываются:

- auth;
- access control;
- CRUD сценарии;
- export endpoints;
- delivery workflows.

### UI checks

Нужны хотя бы для ключевых operator flow:

- opening pages;
- export actions;
- role-aware visibility;
- main layout / navigation / observability entry points.

### Smoke and ops checks

Нужны для ответа на вопрос «система вообще жива?»

- сервисы стартуют;
- worker обрабатывает update;
- БД доступна;
- admin-web видит admin_service;
- экспортные контуры не сломаны.

Общий подход описан в [[09-testing-strategy]] и [[10-ops-runbook]].

## 14. Как развивать проект без хаоса

Ниже несколько правил, которые удерживают систему в рабочем состоянии.

### 14.1. Не чинить parser списком ручных исключений

Если реальная проблема связана с новой позицией, сначала обновляется каталог и структурная логика парсинга, а не добавляется очередной ad-hoc keyword.

### 14.2. Не прятать важную operational логику только во frontend

Все ограничения на аналитику, экспорт и чувствительные действия должны жить на backend тоже.

### 14.3. Не считать Telegram единственным интерфейсом продукта

Бизнес-ядро должно оставаться пригодным для bridge/integration сценариев.

### 14.4. Не делать экспорт «примерно похожим»

Если есть рабочий шаблон, система должна уметь воспроизводить его строго и предсказуемо.

### 14.5. Не держать документацию фрагментированной

При крупных изменениях обновляются минимум:

- этот handbook;
- профильный runbook/reference;
- docs index.

## 15. Репозиторий как карта

Высокоуровневая структура:

- `backend/` — bot/backend core, parser, worker, DB-side domain behavior.
- `admin_service/` — administrative REST API, auth, exports, security boundaries.
- `admin-web/` — React-based operational UI.
- `docs/` — вся документация.
- `samples/` — образцы сообщений и шаблонов.
- `scripts/` — запуск, автоматизация, maintenance.
- `infra/` — docker / infrastructure artifacts.

Если нужно быстро понять кодовую базу:

1. начните с `docs/25-project-handbook.md`;
2. затем `docs/03-architecture.md`;
3. потом смотрите конкретный сервисный каталог;
4. сверяйте бизнес-инварианты по docs, а не только по текущему коду.

## 20. Правило обновления handbook

Этот документ нужно обновлять при изменениях в одной из следующих областей:

- появляется новый сервис или новый transport/provider;
- меняется сквозной поток заказа;
- меняется ролевая или security-модель;
- меняется основной operational workflow;
- меняется тип экспортов или их принципиальная роль;
- меняется логика, влияющая на понимание проекта целиком.

Если меняется только локальная реализация без изменения общей картины, достаточно обновить профильный документ.
